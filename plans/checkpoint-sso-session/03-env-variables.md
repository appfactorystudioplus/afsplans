# 03 — `.env` variables for SSO cookie mode

All variables in this document live in **`apps/auth`'s own `.env` only** —
`_env/{local,vagrant,dev,prod}/.env`, switched via `packages/afsserver/bin/use-env.ps1
<mode>` per `AGENTS.md` §6. The SSO session cookie is entirely internal to Checkpoint: no
other app's `.env` needs any change for this plan. If you find yourself about to add a
`SSO_*` variable to `members`, `coordinator`, or any of the other five apps' `.env` files,
stop — that is a sign the design in [02-design.md](02-design.md) has drifted, not that the
variable belongs there.

**Edit `_env/<mode>/.env`, never the generated root `.env`.** The same trap documented for
the local Parse server in `AGENTS.md` §6 applies here: whichever `.env` is currently active
in `apps/auth/.env` is a copy, regenerated by `use-env`, and a hand-edit to it vanishes on
the next environment switch.

## `SSO_COOKIE_DOMAIN`

| | |
|---|---|
| **Config key** | `checkpoint.sso.cookie_domain` |
| **Current default if unset** | `.appfactory.studio` — wrong in 2 of 4 environments, see [01-current-state-audit.md](01-current-state-audit.md) §4 |
| **Used for** | The `Domain` attribute on the `Set-Cookie: checkpoint_sso=...` header. Must be the `auth` app's own host or a superdomain of it, or the browser silently drops the cookie. |

Set explicitly in every environment, matching the domain shape `auth`'s own `.env` already
declares for that environment:

```env
# _env/local/.env       — auth.test
SSO_COOKIE_DOMAIN=.test

# _env/vagrant/.env     — auth.appfactory.test1
SSO_COOKIE_DOMAIN=.appfactory.test1

# _env/dev/.env         — auth15.appfactory.studio
SSO_COOKIE_DOMAIN=.appfactory.studio

# _env/prod/.env        — auth.appfactory.studio
SSO_COOKIE_DOMAIN=.appfactory.studio
```

**Trap to avoid**: do not compute this from `APP_URL` at runtime instead of setting it
per-environment. It is tempting — `.test`, `.appfactory.test1`, and `.appfactory.studio` are
all mechanically "everything after the first label of the host" — but `dev`'s host
(`auth15.appfactory.studio`) and `prod`'s host (`auth.appfactory.studio`) both reduce to the
same value by that rule, which happens to be correct here but is fragile the moment any
environment gets a host shape that doesn't fit the pattern (e.g. a future `auth.dev.appfactory.studio`
three-label host would compute `.dev.appfactory.studio`, not `.appfactory.studio`, silently
changing which subdomains can share the cookie). An explicit literal per environment, the
same way `CHECKPOINT_BASE_URL` is already handled, has no such edge case.

**Alternative considered and rejected**: leave it unset (host-only cookie, scoped to the
exact `auth` host). This would technically work today, since nothing outside `auth` reads
this cookie ([02-design.md](02-design.md) §2). Rejected per D2 in
[00-overview.md](00-overview.md) — the user asked for this to be a real, dynamic
per-environment setting rather than an implicit default, and an explicit parent domain
costs nothing while leaving room for a future reader on a sibling subdomain.

## `SSO_SILENT_REAUTH_ENABLED` *(new variable)*

| | |
|---|---|
| **Config key** | `checkpoint.sso.silent_reauth_enabled` (new key in `config/checkpoint.php`, alongside the existing `sso` block) |
| **Default if unset** | `false` |
| **Used for** | Gates `AuthController::ssoSession()` ([02-design.md](02-design.md) §2.2). When `false`, the endpoint returns 404 regardless of cookie state — the feature is completely inert, identical to today's behavior. |

This is the rollout lever from D4. Recommended values by phase — see
[04-rollout-and-testing.md](04-rollout-and-testing.md) for the phase definitions:

```env
# _env/local/.env     — Phase 1/2: build and verify here first
SSO_SILENT_REAUTH_ENABLED=true

# _env/vagrant/.env   — Phase 3: verify against the lab's real DNS/nginx/Apache
SSO_SILENT_REAUTH_ENABLED=true

# _env/dev/.env       — Phase 4a: only after local + vagrant have run clean
SSO_SILENT_REAUTH_ENABLED=false

# _env/prod/.env      — Phase 4b: only after dev has run clean
SSO_SILENT_REAUTH_ENABLED=false
```

**Only the user changes `dev`/`prod` values to `true`** — same rule as
`DEVELOPMENT_MODE.md` itself, since flipping this in an environment neither `local` nor
`vagrant` can be verified against means trusting the phase-1–3 testing transfers, which is
exactly the judgment call this flag exists to keep deliberate rather than accidental.

## `SSO_CROSS_APP_LOGOUT_ENABLED` *(new variable)*

| | |
|---|---|
| **Config key** | `checkpoint.sso.cross_app_logout_enabled` (new key, alongside `silent_reauth_enabled`) |
| **Default if unset** | `false` |
| **Used for** | Gates the new, explicit **everywhere-logout** feature only ([02-design.md](02-design.md) §6.2), at a single point: the `POST /checkpoint/auth/logout/all` route returns 404 when disabled, matching §2.2's `ssoSession()` pattern exactly. Since that route is the only way to ever write a revocation-watermark row, the checks in `verifyToken()`/`refreshToken()`/`getTokensFromSsoCookie()` don't need their own separate flag check — with the route disabled, the watermark table stays empty and those checks are harmless no-ops. **Ordinary `logout()` is never gated by this flag, because it never touches any of this** — see D3/§6.1. |

**Independent of `SSO_SILENT_REAUTH_ENABLED`.** These are two separable capabilities —
"log in once, reach every app in this browser" and "an explicit action to log out of every
app and device" — and an operator may reasonably want one without the other while
validating each in turn. Do not collapse them into a single flag, and do not read this
flag's name as implying it changes what the ordinary "Sign out" button does — it does not,
by design (G2).

```env
# _env/local/.env     — Phase 1/2
SSO_CROSS_APP_LOGOUT_ENABLED=true

# _env/vagrant/.env   — Phase 3
SSO_CROSS_APP_LOGOUT_ENABLED=true

# _env/dev/.env       — Phase 4a: only after local + vagrant have run clean
SSO_CROSS_APP_LOGOUT_ENABLED=false

# _env/prod/.env      — Phase 4b: only after dev has run clean
SSO_CROSS_APP_LOGOUT_ENABLED=false
```

Unlike `SSO_COOKIE_DOMAIN`, this flag's *value* doesn't vary by environment's domain shape —
it varies only by rollout phase, the same set of values in the same order as
`SSO_SILENT_REAUTH_ENABLED`, just toggled on its own schedule.

**Secondary-user isolation (G6) is not behind this flag, or any flag.** It is enforced by
the `token_kind` check inside `verifyToken()`/`refreshToken()`/`getTokensFromSsoCookie()`
and by the explicit rejection in `logoutEverywhere()`'s controller method
([02-design.md](02-design.md) §6.4), which runs regardless of
`SSO_CROSS_APP_LOGOUT_ENABLED`'s value — there is no environment or configuration in which
a secondary user's tokens become reachable by the everywhere-logout path. This is
deliberate: isolation between primary and secondary sessions is a correctness property, not
a rollout concern, so it is not something an env var should be able to turn off.

## `SSO_LOGOUT_PROPAGATION_ENABLED` *(new variable)*

| | |
|---|---|
| **Config key** | `checkpoint.sso.logout_propagation_enabled` (new key, alongside `silent_reauth_enabled` and `cross_app_logout_enabled`) |
| **Default if unset** | `false` |
| **Used for** | Gates logout propagation within one browser only ([02-design.md](02-design.md) §7, G10), at a single point: `GET /checkpoint/auth/sso/status` returns 404 when disabled. Every `ClientHandler`'s liveness poll treats a 404 identically to "still logged in" (fail-closed), so disabling this flag silently makes the poll inert everywhere — no other behavior changes. |

**Independent of the other two SSO flags.** Three separable capabilities now share this
cookie: "log in once, reach every app in this browser" (`SSO_SILENT_REAUTH_ENABLED`), "an
explicit action to log out of every app and device" (`SSO_CROSS_APP_LOGOUT_ENABLED`), and "log
out of one app, and every other app *already open in this browser* notices" (this flag). An
operator may reasonably want any one without the others while validating each in turn.

```env
# _env/local/.env     — Phase 1/2
SSO_LOGOUT_PROPAGATION_ENABLED=true

# _env/vagrant/.env   — Phase 3
SSO_LOGOUT_PROPAGATION_ENABLED=true

# _env/dev/.env       — Phase 4a: only after local + vagrant have run clean
SSO_LOGOUT_PROPAGATION_ENABLED=false

# _env/prod/.env      — Phase 4b: only after dev has run clean
SSO_LOGOUT_PROPAGATION_ENABLED=false
```

## Variables that already exist, need **no** per-environment change, but are worth confirming explicitly

### `SSO_COOKIE_SECURE`, `SSO_COOKIE_HTTPONLY`, `SSO_COOKIE_SAMESITE`

| | |
|---|---|
| **Config keys** | `sso.cookie_secure` (default `true`), `sso.cookie_httponly` (default `true`), `sso.cookie_samesite` (default `Lax`) |
| **Set to** | Leave unset (i.e. keep the defaults) in **all four** environments |

**Trap to avoid**: do not set `SSO_COOKIE_SECURE=false` for `local` on the assumption that a
local dev environment can't do HTTPS. It can and does — Laragon serves every `.test` vhost
over HTTPS with its own self-signed pair (`AGENTS.md` §6). Weakening `Secure` for `local`
would be an unforced security regression solving a problem that doesn't exist here, and
would make `local` the one environment where this cookie behaves differently in a way that
could hide a bug that only reproduces with `Secure` actually enforced.

### `SSO_COOKIE_LIFETIME`

| | |
|---|---|
| **Config key** | `sso.cookie_lifetime` (default `2592000` = 30 days) |
| **Set to** | Leave as the global default in all four environments, for this plan |

Not environment-specific — how long a silent session should last is a product decision
independent of which machine is running the code. [02-design.md](02-design.md) §5 flags
this value (and whether it should be shorter on a *password change* with no explicit
logout) as an open follow-up, not something to change as part of wiring the plumbing back
up. Note that revocation *on logout* is now handled separately by
`SSO_CROSS_APP_LOGOUT_ENABLED` regardless of this cookie's own lifetime — the two are not
the same mechanism.

## Variable that exists, is unrelated to this plan, and should not be touched

### `SSO_MODE`

Already `ticket` in all four environments; stays `ticket` everywhere. Per D1 in
[00-overview.md](00-overview.md), this plan adds a cookie-backed *check* in front of ticket
delivery — it does not switch the platform to `getSsoMode()`'s `'cookie'` branch, which
(per [01-current-state-audit.md](01-current-state-audit.md) §6) is dead code with a
different, unrelated meaning in this codebase's history. Do not repurpose it for this
plan's flag; that is exactly why `SSO_SILENT_REAUTH_ENABLED` is a new variable instead of
an overload of this existing one.

## Summary table

| Variable | New or existing | Differs per environment? | This plan sets it in |
|---|---|---|---|
| `SSO_COOKIE_DOMAIN` | Existing, currently unset everywhere | **Yes — 3 distinct values** | All four `_env/<mode>/.env` |
| `SSO_SILENT_REAUTH_ENABLED` | **New** | **Yes — the rollout gate for silent sign-on** | All four, values changing over time per phase |
| `SSO_CROSS_APP_LOGOUT_ENABLED` | **New** | **Yes — the rollout gate for cross-app logout, independent of the above** | All four, values changing over time per phase |
| `SSO_LOGOUT_PROPAGATION_ENABLED` | **New** | **Yes — the rollout gate for same-browser logout propagation, independent of both above** | All four, values changing over time per phase |
| `SSO_COOKIE_SECURE` / `_HTTPONLY` / `_SAMESITE` | Existing | No — keep defaults everywhere | Nowhere (confirmed correct as-is) |
| `SSO_COOKIE_LIFETIME` | Existing | No, for this plan | Nowhere (confirmed correct as-is) |
| `SSO_MODE` | Existing, unrelated | No | Nowhere (out of scope, do not repurpose) |

Secondary-user isolation is enforced in code (`token_kind`), not by any variable in this
table — see the callout at the end of the `SSO_CROSS_APP_LOGOUT_ENABLED` section above.
