## Summary

- **P0 — keys.** Members mints RS256 tokens (`TokenMinter`); its private key exists only there (`storage:token-key-generate`
  writes it 0600 and never prints it). The Brain stores members' **public** keys by `kid` (`brain_storage_token_keys`,
  staff API, RSA ≥ 2048 only, a private key or anything containing "PRIVATE" is refused, the last active key cannot be
  retired, a `kid` is never reused) and publishes them in each server's config document, keeping a retired key for a
  grace window (default 1 h) so tokens in flight still verify.
- **P0 — control key, and a correction to the plan.** The plan had one members→storage key shared by every storage
  app. That lets one compromised server forge control calls to every other, which contradicts [08](../08-security.md) §6.
  Instead the Brain and members hold a **master** and each server is given only `HMAC(master, "afs-storage-control:v1:" +
  server_reference)`. Members derives the key for whichever server hosts the device (read-only registry lookup that
  never touches the credential columns). Rotation: set a `next` master, both are derived and accepted, then promote.
- **P1.** Opening a session places it, then sends the signed grant to the device **before answering**. Grant failure, or a
  token that cannot be minted, releases the reservation, marks the session `failed`, cancels any orphaned grant and
  returns `503 STORAGE_UNAVAILABLE`. The 201 gains `upload_url`, `upload_token`, `upload_token_expires_at`. Members
  refuses the bytes (`421 UPLOAD_ON_DEVICE`) and reports no offsets. Commit calls the device and writes node rows only
  for files of that session the device reports committed **at the granted size**; a device cannot create a row for a file
  it was never granted.
- **P2.** `POST /sessions/{id}/upload-token` (re-checks ownership, expiry, state); `GET /files/{id}/download-url`
  returns `{url, token, expires_at}` (404 not 403, 423 purging bucket, 409 for a legacy local file); the old
  `/content` route answers `421 DOWNLOAD_ON_DEVICE` for a device file.

The end-to-end run: members opens a session (real grant to the device), three 1200-byte chunks go straight to the device
with the upload token, members commits, the file is on disk at its real name under the device mount and the node row
carries the device, and a download returns the whole file and a `206` range. Also over real HTTP: an expired token gives
`TOKEN_EXPIRED` → refresh → resume from the device's offset → commit; wrong-device, download-as-upload and another
member's token are refused (404 for the other member); a forged control call is 401; a grant for `../../etc/passwd` sent
straight to the device is `422 PATH_REJECTED`; the device unreachable at open is `503` with the reservation released and
at commit is `503` with the session still open, and both recover.

  step 10's cross-device operations exist.
- **Ops fan-out** (move / rename / delete across devices, and the `members_storage_operations` journal) — step 04 P3 and

## To use it (when you choose to)

1. In members `.env`: `STORAGE_BASE_DOMAIN`, `STORAGE_CONTROL_MASTER_KEY` (from `php artisan storage:control-key-generate`),
   `STORAGE_TOKEN_KID` + `STORAGE_TOKEN_PRIVATE_KEY_PATH` (from `php artisan storage:token-key-generate {kid}`).
2. In the Brain (API only for now): `POST /portal/api/v1/brain/storage/token-keys {kid, public_key}` and
   `PUT /portal/api/v1/brain/storage/members-key {key}` with the same master.
3. Run the migration `2026_09_27_000004_create_brain_storage_keys_tables.php` (not run anywhere real).
4. Only then `STORAGE_PLACEMENT_ENABLED=true`.
