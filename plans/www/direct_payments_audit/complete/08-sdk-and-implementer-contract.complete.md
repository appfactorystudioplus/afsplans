# 08 — SDK and Implementer Contract (complete — written, type-checked and tested at the seams; the SDK was never run in a browser)

## Status

**Complete 2026-10-17.** Nothing is committed. Said plainly first: **no browser ever ran this SDK.** What is verified is that it compiles (`tsc --noEmit`, both projects), that the request layer it is built on behaves as specified (a node test of `RequestContext`, 6 tests), that the server answers the way the SDK now relies on (PHP tests below), and that the source no longer contains what the contract forbids (a test that reads the SDK source). The re-mount of the payment form after a processor change (`_handleProcessorChange`, `_withBinding`, the `confirmPayment` branch) is **not covered by any test**: `api.ts` uses TypeScript parameter properties, which the repository's node test runner cannot load, and there is no jsdom suite for it. It is the first thing to try in a browser: open the single-charge sample, lock an invoice, change the processor in the admin, press Pay.

Also not done: **TODOS P2.2** ("each sample builds the invoice first and shows the dynamic-price case") belongs to the separate server-owned-invoice plan (TODOS P0–P2) and is outstanding there; the samples here were updated only for this step's changes.

## Deviations and residue

* **Re-issuing after a change happens only where no typing is needed.** §8.3 says the SDK "re-issues the call once". For mounting a form (`setup*`) it does. For `confirmPayment` it cannot: the visitor's card details were typed into the old provider's form and cannot be sent to the new one, so it mounts the new form and returns a failure the page already knows how to show (`remounted: true`).
* **The SDK still pays through the processor-addressed routes** (create-intent, create-order, create-payment), now carrying `direct_payment_reference_num` and the version, and relies on step 06's shim to refuse a stale processor. The new Direct-Payment-addressed `…/invoices/{inv}/pay` exists and is tested on the server but the SDK does not call it yet — the provider clients' flows (deferred intents, PayPal buttons, Square tokenise-then-charge) would each need restructuring for that.
* `charge()` is a breaking removal of something that never worked; the sponsors dashboard (`resources/js/portal/sponsors/dashboard.ts`) calls it and will now show the error instead of a failed request.
* `resources/js/afs/create.ts` (appfactory sign-up) no longer sends a customer id; the server finds the customer from the subscription's payer. That sign-up belongs to step 14.
* The playground `marketplace_split`, `connect_setup` and `dashbaord` samples needed no change for this step.
* The Direct Payments README mentions the contract's `reauthorise()` flow; nothing in the playground demonstrates it yet (it needs a processor change in progress).
