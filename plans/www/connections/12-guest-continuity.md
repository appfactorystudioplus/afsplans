# 12 — Guest Continuity

What a guest can get back to, and how they get back to it. Two defects found in the plan
review (**X25**, **X26**), both pre-existing, both folded in here because the rest of this
plan quietly depends on a guest having *something* to return with.

Connecting a module is optional, and guest checkout stays the baseline
([00](00-overview.md) §2, goal 6). So the guest path is not the degraded case — for most instances
it is the **only** case, and it has to work before an account is an improvement on it.

## 12.1 What tracks a guest today

Four mechanisms, one per module, three storage layers, and nothing shared. Read from the code
on 2026-09-12.

| Module | The identifier | Generated by | Lives in | Survives |
|---|---|---|---|---|
| Ecommerce, before purchase | `carts.cart_token` | `EcommerceReference::cartToken()` — `Str::random(32)` | `ec_cart_token` cookie, 30 days, httpOnly, `Lax`, `secure` per `config('session.secure')` | Tab close. Not a device change |
| Ecommerce, after purchase | `orders.reference_num` | `EcommerceReference::order()` — `ord_` + `Str::lower(Str::random(12))` | The URL of the confirmation page (`?order=`) | Nothing keeps it |
| Events | `registrations.access_token` | `EventReference::accessToken()` — `Str::random(48)` | The row; returned once in the `register()` response | Nothing keeps it |
| Appointments | `bookings.access_token` | `AppointmentReference::accessToken()` — `Str::random(48)` | The row; returned once in the `book()` response | Nothing keeps it |
| Direct Payments | the anonymous provider customer | `POST /customers/create-anonymous` | `sessionStorage['afs_customer_id_<dpRef>']` + a `laravel_processor_customers` row with `email = ''` | A reload. Not a new tab |

**Token strength is not the problem.** A 48-character base62 token and a 32-character cart
token are far past guessable, and a 12-character lowered order reference still carries about
sixty bits — enough that enumeration is not the risk. The ecommerce order endpoint
deliberately lets anyone holding the reference read a *guest* order, which is how a receipt
link has to work ([ecommerce/01](../ecommerce/01-site-users-guard.md) §1.4).

The problem is upstream of the tokens: one of them is destroyed by a second store, and three
of them are never delivered to the person who needs them.

## 12.2 X25 — two stores on one site share one cart cookie, and the second destroys the first

`EcommerceCartCookie::NAME` is the constant `'ec_cart_token'` for the whole deployment, while
`carts.cart_token` carries a **global** unique index and every lookup filters by store:

```php
// EcommerceCartService::findActiveByToken()
->where('store_reference_num', $storeRef)->where('cart_token', $token)->where('status', 'active')

// EcommerceCartService::getOrCreate() — the destructive line
if ($token !== null && EcommerceCart::query()->where('cart_token', $token)->exists()) {
    $token = null;                      // ← mints a NEW token, which overwrites the cookie
}
```

A guest with a cart at store A arrives at store B. `findActiveByToken(B, T)` misses,
`where('cart_token', T)->exists()` hits, the token is discarded, a new cart is created with a
new token, and `withCartCookie()` writes that new token over the cookie. **Store A's cart
still exists in the database and the browser can no longer address it.**

This matters to *this* plan specifically: a public retail store beside a members-only
wholesale store is the worked example behind K2's precedence rule
([02](02-architecture.md) §2.3) and [ecommerce/01](../ecommerce/01-site-users-guard.md)
§1.5.2. The plan actively encourages the configuration that triggers the bug.

### The fix — the token identifies the *browser*, not the cart

Carts become unique per `(store, token)`, so one shopper token addresses one cart in each
store and the cookie never has to change.

The obstacle is the converted cart: after checkout the row keeps `status = 'converted'` and
would still hold the token, so a second purchase at the same store would collide. The
codebase already has the answer to exactly this shape — `laravel_appointment_bookings`
carries `active_slot_key`, nullable and unique, set while the booking is live and **nulled on
cancellation** (`AppointmentBookingService::cancel()`), because MySQL treats NULLs in a unique
index as distinct. Carts get the same treatment:

```php
/**
 * AFS_ECOMMERCE_MODIFIER_ADDITION — plans/www/connections/12-guest-continuity.md §12.2 (X25).
 *
 * `cart_token` identifies the BROWSER, not the cart, so one shopper holds one
 * token across every store on the site. Uniqueness therefore moves off
 * `cart_token` and onto `active_cart_token`, which mirrors it only while the
 * cart is active — the same nullable-unique pattern
 * `laravel_appointment_bookings.active_slot_key` already uses, for the same
 * reason: MySQL counts NULLs as distinct, so a converted cart frees its slot
 * without releasing the browser's token.
 */
Schema::table('laravel_ecommerce_carts', function (Blueprint $table) {
    if (! Schema::hasColumn('laravel_ecommerce_carts', 'active_cart_token')) {
        $table->string('active_cart_token', 64)->nullable()->after('cart_token');
    }
});

// Backfill before the index: every active cart mirrors its token, everything else is NULL.
DB::table('laravel_ecommerce_carts')->where('status', 'active')
    ->update(['active_cart_token' => DB::raw('cart_token')]);

Schema::table('laravel_ecommerce_carts', function (Blueprint $table) {
    $table->dropUnique('laravel_ecommerce_carts_cart_token_unique');   // the global unique goes
    $table->index('cart_token', 'ec_carts_token_idx');                 // still queried, no longer unique
    $table->unique(['store_reference_num', 'active_cart_token'], 'ec_carts_store_active_token_uq');
});
```

Three code changes, and no others — `cart_token` is read in exactly two places, both of which
already filter by store (verified: `grep -rn "where('cart_token'" app/`):

```php
// 1. getOrCreate() — reuse the browser's token instead of discarding it.
//    Uniqueness is now per (store, active), so the same token in another store is correct.
$cart = EcommerceCart::query()->create([
    'reference_num'     => EcommerceReference::cart(),
    'store_reference_num' => $storeRef,
    'cart_token'        => $token ?? EcommerceReference::cartToken(),
    'active_cart_token' => $token ?? /* the same value */,
    'currency'          => $store->currency ?? 'usd',
    'status'            => 'active',
    'expires_at'        => now()->addDays(30),
]);

// 2. createCartForSiteUser() — same two columns.

// 3. Every status transition off 'active' nulls the active column, in the same
//    write that changes the status: EcommerceCheckoutService::complete()
//    (converted), the abandonment sweep (expired), and cart clearing where it
//    closes a cart rather than emptying it.
$cart->status = 'converted';
$cart->active_cart_token = null;
```

`resolveCartForShopper()` and the sign-in merge are untouched: they already work per store,
and a stable token makes the merge *more* correct, not less — a guest with carts at two stores
who signs in now has both merged into their account, one per store, instead of one merged and
one silently abandoned.

### Why not a cookie per store

`ec_cart_token_<storeRef>` would also work and needs no migration. It is rejected because
cookie count grows with the catalogue, the name becomes a place a store reference leaks into
the browser, and every existing guest cart is orphaned on deploy. The token-identifies-the-
browser model keeps one cookie, keeps every existing cart addressable (the backfill mirrors
the current token), and matches how the same problem was already solved next door.

## 12.3 X26 — the receipt is generated and never sent

A guest's `access_token` is created, returned once in the HTTP response, and then dropped.
Both confirmation services are stubs:

```php
// EventCommunicationService::sendConfirmation()
Log::info('events.confirmation', ['registration_ref' => …, 'email' => …]);

// AppointmentCommunicationService::sendConfirmation()
Log::info('appointments.confirmation', ['booking_ref' => …, 'email' => …]);
```

Neither carries the token even into the log. Ecommerce sends nothing at all — there is no
mail call anywhere in `app/Externals/Ecommerce/`. And the storefront does not persist it either: the
events UI holds it in `pendingToken`, a module-scoped variable that dies on navigation, and
the receipt shows only the registration reference.

**So today a guest who closes the tab cannot reach their registration or booking at all**, and
reaches their order only if they still have the URL. Every "manage your booking" affordance in
[09](09-module-self-service.md) is reachable by an account holder and by nobody else.

This is a pre-existing gap, not one this plan creates. It is folded in because
[09](09-module-self-service.md) §9.7's claim service — the thing that gives a guest their
history once they register — is otherwise the *only* route back that works, and it requires
the guest to register, verify an email, and match on an address they typed correctly.

### What is in scope here, and what is not

| | Owner |
|---|---|
| **One transactional receipt per purchase**, carrying a working link back | **This document** |
| Where the link points — resolving a module's published pages | **This document**, §12.4 |
| The storefront rendering that link's destination for a guest | **This document**, §12.6 |
| Branding, templates a tenant can edit, multi-language | [events/10](../events/10-communications.md), [appointments/10](../appointments/10-communications-and-calendar.md), [ecommerce/08](../ecommerce/08-orders-and-fulfilment.md) §8.7 |
| Reminders, scheduled sends, dunning | the same three, plus [direct_payments/24](../direct_payments/24-notification-scheduler.md) |

The line is: **this plan makes the token reach the person; it does not build a notification
system.** One plain Mailable per module, mirroring the one Site Users already ships.

### The mailables

`SiteUsersTokenMail` is the pattern to copy — a `Mailable` with a Blade view, sent through
Laravel's configured mailer, which is `MAIL_MAILER=log` locally so the link lands in
`storage/logs/laravel.log` and the flow is verifiable without SMTP.

```php
/**
 * AFS_EVENTS_MODIFIER_ADDITION — plans/www/connections/12-guest-continuity.md §12.3 (X26).
 *
 * The registration receipt. Mirrors App\Mail\SiteUsers\SiteUsersTokenMail:
 * a Mailable, a Blade view, Laravel's configured mailer, no scheduler.
 *
 * `manageUrl` is the ONLY way a guest reaches their registration again, so a
 * send failure is logged loudly — but never thrown, because the registration is
 * already committed and paid for and must not be rolled back by a mail
 * transport (the same rule SiteUsersVerificationService::deliver() follows).
 */
class EventRegistrationReceiptMail extends Mailable
{
    public function __construct(
        public string $eventName,
        public string $attendeeName,
        public string $occurrenceStartsAt,
        public string $ticketCode,
        public string $manageUrl,
        public ?string $calendarUrl,
    ) {}
}
```

`AppointmentBookingReceiptMail` and `EcommerceOrderReceiptMail` are the same shape. Each
service's `sendConfirmation()` keeps its existing `Log::info` **and** its activity-log write
(appointments already logs `email.confirmation.sent`), and gains the send inside a `try`:

```php
public function sendConfirmation(EventRegistration $registration): void
{
    Log::info('events.confirmation', [
        'registration_ref' => $registration->reference_num,
        'email' => $registration->attendee_email,
    ]);

    if (! $registration->attendee_email) {
        return;
    }

    try {
        Mail::to($registration->attendee_email)->send(new EventRegistrationReceiptMail(...));
    } catch (\Throwable $e) {
        // Never rethrow: the registration is committed and the place is claimed.
        Log::error('[events] receipt failed to send', [
            'registration_ref' => $registration->reference_num,
            'error' => $e->getMessage(),
        ]);
    }
}
```

Ecommerce has no confirmation service at all, so it gains the smallest one that can exist —
`App\Externals\Ecommerce\Services\EcommerceReceiptService::sendOrderReceipt(EcommerceOrder $order)`,
called from `EcommerceCheckoutService::complete()` **after** the transaction commits, never
inside it.

## 12.4 Where a module's pages are — one resolver, not four

[04](04-connection-registry-and-enforcement.md) §4.6 introduced `SiteUsersPagePaths` to answer
"where is this module's login page" from the `laravel_builder_routes` row the Dashboard
publish writes. A receipt needs the same question for a *consuming* module: where is this
store's order page, this event's registration page, this calendar's booking page.

The answer is already indexed. `laravel_builder_module_refs` maps
`(module_id, instance_ref) → (project_reference_num, subpaths)`, and joining it to
`laravel_builder_published` on `is_active = 1` gives the pages that are live right now — the
same join `BuilderController::moduleRefUsage()` already runs for the admin's "used on N pages"
count.

```php
/**
 * AFS_SITE_USERS_MODIFIER_ADDITION — plans/www/connections/12-guest-continuity.md §12.4.
 *
 * "Where does this instance's published page live?" Generalises
 * SiteUsersPagePaths (04 §4.6) so one class answers it for every module.
 *
 * Subpage slugs follow the builder's sibling convention — `<base>-<subpage>`,
 * the rule `siblingHref()` and `suHref()` already encode — so one known subpath
 * yields all of them: strip a known suffix, append the wanted one.
 *
 * Resolution order, most specific first:
 *   1. the connection's `settings.pages.<subpage>` override (05 §5.5)
 *   2. a live laravel_builder_module_refs row for this instance
 *   3. a live row for ANY instance of this module (a shared storefront page)
 *   4. null — the caller falls back to config('app.url') and omits the link
 */
final class ModulePagePaths
{
    /** @return array<string, string>  subpage => absolute URL */
    public function forInstance(string $moduleKey, ?string $instanceRef): array;
}
```

Step 4 matters: a tenant using the externals SDK on their own site has **no** builder page,
so there is nothing to link to. The receipt then omits the manage link entirely and says so in
words rather than emitting a broken URL — and the connection's `settings.pages` override
([05](05-admin-connections.md) §5.5, which already carries `login_path`) is how that tenant
supplies their own.

`SiteUsersPagePaths` becomes a thin caller of this class rather than a second implementation.

## 12.5 What is safe to put in the link

The token in a URL is a bearer credential, so the rules are the ones that already govern the
emailed booking link ([appointments/02](../appointments/02-site-users-guard.md) §2.5):

| Rule | Why |
|---|---|
| The link grants **one record**, never a list | A token is not a session. `GET /registrations/{ref}?t=` is already scoped to one row |
| **Never log the full URL** — log the reference, not the token | The current `Log::info` lines already do this correctly; the mailables must not regress it |
| The token is **not** in the ICS file | `buildIcs()` does not include it today. Keep it that way — calendar files get forwarded and synced |
| A **signed-in** purchaser gets a dashboard deep link instead, with no token | They have a durable route back ([08](08-dashboard-sections.md) §8.4's hash form). Minting a second credential for someone who does not need one is pure downside |
| The guest's email is **unverified free text** | A typo sends the token to a stranger. Inherent to guest checkout; the mitigation is that the token reaches exactly one record and can do exactly what that record's connection settings allow |

That last row is worth stating plainly rather than engineering around: requiring verification
before a guest receipt would mean no receipt, which is worse. What it rules out is putting
anything in the receipt beyond that single purchase — no account links, no order history, no
other records for the same address.

## 12.6 The guest's destination

Both API and SDK already support the token path — `registration(ref, token)`,
`cancelRegistration(ref, token)`, `booking(ref, token)`, `cancelBooking(ref, token)`,
`reschedule(ref, startsAt, token)`, `calendarUrl(ref, token)` all exist and all pass
`access_token`. Only the page rendering is missing.

So the `my-registrations` and `my-bookings` subpages gain one branch, and no new subpage is
created:

```ts
/**
 * AFS_BUILDER_MODIFIER_ADDITION — plans/www/connections/12-guest-continuity.md §12.6.
 *
 * One page, two audiences. `?registration=<ref>&t=<token>` is the guest's
 * emailed link and renders exactly that record; no query string means the
 * signed-in list (04 §4.4, which now 401s for a guest). A guest who follows the
 * link and later signs in sees the list — the token path never blocks the
 * account path.
 */
async function renderMyRegistrations(root: HTMLElement): Promise<void> {
    const params = new URLSearchParams(window.location.search);
    const ref = params.get('registration') || '';
    const token = params.get('t') || '';

    if (ref && token) {
        const record = await api.registration(ref, token);
        root.innerHTML = buildSingleRegistrationMarkup(record);   // pure builder, K14
        wireGuestActions(root, ref, token);                        // cancel, calendar — policy applies (09 §9.3)
        return;
    }
    // …the existing signed-in list…
}
```

Ecommerce needs no branch: its order-confirmation subpage already reads `?order=` and the
endpoint already serves a guest order by reference.

**A disconnected instance makes this view read-only too** ([13](13-disconnection.md) §13.5,
X41). The single-record serializers carry `read_only` and `read_only_notice`; when set, the
pane renders the notice and `wireGuestActions()` is not called. The rule is about the
instance, not about who is asking, so a guest and a signed-in user see the same thing.

`buildSingleRegistrationMarkup()` and its appointments twin are exported pure builders in the
module's `ui.ts`, like everything else (K14) — and the dashboard's detail panes
([08](08-dashboard-sections.md) §8.5) render the **same** builders with an owner-resolved
record. One markup, two callers, which is the point of
[builder/v2/09](../builder/v2/09-single-source-ui.md).

## 12.7 What this does not fix

- **A guest who gives a wrong email still loses their record.** No mechanism recovers that;
  the operator finds it in the admin by name or date.
- **The Direct Payments `sessionStorage` customer is still per-tab.** A guest opening checkout
  in a second tab mints a second anonymous provider customer. Unchanged by this plan and
  harmless — an unused anonymous customer costs nothing, and a *signed-in* checkout no longer
  goes down that path at all ([07](07-direct-payments-connection.md) §7.3).
- **No receipt resend.** A guest cannot ask for the link again without contacting the tenant,
  because a resend endpoint keyed on an email address is an enumeration oracle for "did this
  person buy". The admin can resend from the record. [11](11-rollout-and-testing.md) §11.7
  follow-up 14.

## 12.8 Acceptance

**X25 — the cart cookie**

- A guest adds a line at store A, then at store B, then returns to store A: **both carts are
  intact**, and the cookie value never changed.
- Completing checkout at store A nulls that cart's `active_cart_token`; the next visit to
  store A creates a fresh cart under the **same** cookie token.
- Two active carts in the same store with one token is refused by
  `ec_carts_store_active_token_uq`.
- Signing in merges the guest cart **per store** — a shopper with carts at two stores keeps
  both.
- The migration backfills every existing active cart, so no guest loses a cart on deploy.
- `grep -rn "where('cart_token'" app/` still shows exactly two call sites, both store-scoped.

**X26 — the receipt**

- A guest registration, booking and order each produce one email through the configured
  mailer; with `MAIL_MAILER=log` the link is in `storage/logs/laravel.log`.
- Following that link renders the single record and allows exactly the actions its
  connection's settings permit ([09](09-module-self-service.md) §9.3, §9.4).
- A **signed-in** purchaser's receipt contains a dashboard link and **no token** — asserted by
  a string check on the rendered mail body.
- The full URL never appears in any log line; the reference does.
- A mail-transport failure logs an error and **does not** roll back the registration, booking
  or order — asserted by forcing the mailer to throw and checking the row still exists.
- An instance with no published page and no `settings.pages` override sends a receipt with no
  manage link and no broken URL.
- The ICS attachment contains no token.
- A guest link to a record on a **disconnected** instance renders the record plus the
  read-only notice, with no action controls ([13](13-disconnection.md) §13.5).
