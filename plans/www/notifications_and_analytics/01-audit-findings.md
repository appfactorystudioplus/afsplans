# 01 — Audit Findings

How this was done: every file named below was read in full or in the relevant range on 2026-10-19; callers were found with `grep` scoped to `app/`, `routes/`,
`resources/js/` and `tests/`. **Nothing was executed against a server or a database.** A finding marked **(inferred)** follows from reading the code and
Laravel's documented behaviour and has not been proved by a test; [09](09-rollout-and-testing.md) phase P0 writes the failing test first.

Severity: **High** — wrong or unsafe today for a user; **Medium** — a defect or a missing capability the plan depends on; **Low** — hygiene.

## 1.1 The admin inbox — `N1`–`N10`

The inbox is `laravel_notifications` ([`database/migrations/2026_04_14_000001_create_laravel_platform_tables.php`](../../../../../w/www/database/migrations/2026_04_14_000001_create_laravel_platform_tables.php)
lines 50–62), the model `App\Models\Notification`, `NotificationApiController`, and the dashboard's `NotificationService.ts`.

| ID | Finding | Evidence | Consequence | Severity |
|---|---|---|---|---|
| **N1** | **"Mark all read" cannot reach its endpoint.** `PATCH /notifications/{id}` is declared before `PATCH /notifications/mark-all-read` and has no `where()` constraint, so Laravel matches the request to `{id}` = `mark-all-read`, `update()` returns 404, and the client falls back to a local-only update that the next poll reverses. **(inferred — Laravel matches routes in declaration order)** | `routes/portal.php:865` then `:866`; client `NotificationService.ts` `markAllAsReadAsync()` ~1142–1165 (falls back to `markAllAsRead()` on a non-OK response) | The button visibly works for ≤15 seconds, then every notification is unread again | High |
| **N2** | **Message text is rendered into `innerHTML` unescaped.** `${n.title}` and `${n.message}` are interpolated into HTML strings in the dropdown and in the full list. One producer builds `body` from sponsor-typed text (`$validated['notes']`, up to 2000 characters) | `NotificationService.ts:744`, `:748`, `:1272`, `:1274`; producer `SponsorPortalController.php:339–342` | Stored cross-site scripting in the admin dashboard: a sponsor can run script in an administrator's session | High |
| **N3** | **The notification `type` (info / success / warning / danger) is never stored.** The client reads `raw.type`, the table has no such column, so every notification is styled `info` | `NotificationService.ts:172`; migration lines 50–62 | Severity cannot be expressed; failures look like good news | Low |
| **N4** | **Only the newest 20 notifications are ever fetched.** The list endpoint defaults to `limit = 20`; the client calls it with no `page` or `limit`, and computes the unread badge from what it received | `NotificationApiController::list()` line 119 (`limit` default 20); `NotificationService.ts:476` | Unread older than the newest 20 are invisible and uncounted | Medium |
| **N5** | **One shared inbox.** A row has no recipient and `is_read` is a single flag: the first administrator to read a notification reads it for everyone | `App\Models\Notification` ($fillable has no recipient); migration | No per-admin state, no way to notify only the site owner | Medium (design limit) |
| **N6** | **Two of the three producers are wrong.** `ProcessFormSubmission::createAdminNotification()` is correct. `SponsorshipApplicationController::dispatchAdminNotification()` writes `type`, `message`, `data`, `read` — none are columns and none are `$fillable`, so Eloquent drops them and the row has a title and nothing else **(inferred)**. `SponsorPortalController::notifyEvent()` passes `metadata` as a PHP array to a `text` column with no `$casts`, which fails the insert **(inferred)** | `ProcessFormSubmission.php:53–76`; `SponsorshipApplicationController.php:297–310`; `SponsorPortalController.php:339–352`; `App\Models\Notification` (no `$casts`) | Sponsorship notifications are lost or empty | Medium |
| **N7** | **No dedupe.** Nothing stops a retried job or webhook from creating the same notification twice | `laravel_notifications` has no unique key; `Notification::create()` is a plain insert | Duplicate rows | Medium |
| **N8** | **Click-through exists for two categories only.** `buildNavigatePayloadFromNotification()` routes `forms` and `commerce`; every other category — including `DIRECT_PAYMENTS`, `EVENTS`, `APPOINTMENTS`, `SUBSCRIBER` — returns `null`, and the stored `link` is ignored | `NotificationService.ts:322–354` | A notification about a payment cannot take the admin to the payment | Medium |
| **N9** | **Sample notifications are injected in production.** When the local cache is empty the constructor adds "Welcome!" and "System Update" with random ids; marking one read sends a `PATCH` for an id the server does not have | `NotificationService.ts:90–96`, `:890–901` | A new administrator sees invented messages that cannot be dismissed | Low |
| **N10** | **No tests, no retention.** No test references `NotificationApiController` or the client service; the table grows forever; "Clear all" is local-only and reverses on the next poll | `grep` in `tests/`; `NotificationService.ts:1177–1186` | Regressions are invisible; unbounded growth | Low |

## 1.2 The dispatcher and e-mail — `M1`–`M10`

| ID | Finding | Evidence | Consequence | Severity |
|---|---|---|---|---|
| **M1** | **`NotificationDispatcher` is general in name and Direct Payments in every line.** It imports `DirectPaymentNotification`, `DirectPaymentNotificationSend`, `DirectPaymentSubscription`, `DirectPaymentPayer`, `DirectPayment`, `ProcessorSubscription`, `ProcessorCustomer`, `ProcessorPlan`; its scheduled query joins `laravel_processor_subscriptions`; its variables are `plan_name`, `card_brand`, `next_charge_date`, `access_ends_at`; recipients come from the payer then the provider customer | `app/Externals/DirectPayments/Notifications/NotificationDispatcher.php` lines 5–16, 62–70, 222–266, 357–400; callers: `ProcessorWebhookController`, `DirectPaymentSubscriptionController`, `DirectPaymentsSubscriptionNotify` | No other module can use it without copying it | High (for this plan) |
| **M2** | **One payment can send two e-mails through two mechanisms.** `invoice.payment_succeeded` calls `dispatchEvent('payment_succeeded')` (needs an active notification row); `charge.succeeded` calls `ChargeSucceeded::handle()`, which queues `SendDirectPaymentMail` → `DirectPaymentCommunicationService` (the receipt). A Direct Payment configured with both gets both | `ProcessorWebhookController.php:634–639` and `ChargeSucceeded.php:24–52`; `DirectPaymentCommunicationService::paymentSucceeded()` | Duplicate e-mail; no single "the payment e-mail" | Medium |
| **M3** | **Nothing configured means nothing sent.** The built-in default template is reachable only through a notification row (`payment_receipt` active with no handler). With no row and no attached handler, the receipt service sends nothing. And the other modules have **no per-event setting at all**: Events, Appointments, Ecommerce and Site Users each send *every mail handler attached to the item* (`MailHandlerModel::where('item_reference_num', …)`), with no switch | `DirectPaymentCommunicationService.php:49–69`; `EventCommunicationService::sendConfirmation()` ~56–72 and the same shape in the Appointments, Ecommerce and Site Users mailers | A new site is silent until configured; modules cannot turn a single e-mail off | Medium |
| **M4** | **Three send paths.** `MailHandlerSender::send()` reads the main configuration and calls the Brain over HTTP (`getBrainConfig()`) **on every send**. `BillingMailer` resolves both **once per instance** and carries the hardening fixes B9, B24 and B25. The dispatcher sends through `DirectPaymentMailer` → `MailHandlerTransport` → `MailHandlerSender` — not through `BillingMailer`, although `24-notification-scheduler.md` §6.6 describes `BillingMailer` | `MailHandlerSender.php:29–35`; `BillingMailer::resolveOnce()` ~33–60; `NotificationDispatcher.php:27, 200`; `DunningService` still uses `BillingMailer` | A 15-minute run that sends 100 e-mails makes 100 configuration reads and up to 100 HTTP calls to the Brain | Medium |
| **M5** | **`failed` ledger rows are never retried and there is no way to resend.** This is deliberate (24 §6.10), but the admin panel that would hold a "resend" button does not exist — and no admin script calls the `…/notifications/sends` endpoint at all | `insertPendingLedgerRow()` returns null on the unique key; `24-notification-scheduler.md` §6.8, §6.10; `grep -rn "notifications/sends" resources/js/portal/admin` is empty | A transient provider outage loses that period's reminder permanently | Low (by design) |
| **M6** | **Dispatcher behaviour is tested only by reflection on private methods.** `resolveCustomerEmail` and `buildVars` are invoked through `ReflectionMethod`; no test sends through `dispatchEvent` or `evaluateScheduled` end to end | `tests/Feature/DirectPayments/ExtensionPointsTest.php:285–312`; `grep` in `tests/` | An extraction cannot prove it changed nothing | High (risk to this plan) |
| **M7** | **The event vocabulary lives in six places.** `DirectPaymentNotification::EVENTS` (+ `ALWAYS_ON_EVENTS`, `SCHEDULED_EVENTS`); the `<select>` in `directpayments-form.html`; and in `directpayments.ts` three more lists — `SINGLE_PAY_NOTIFICATION_EVENTS`, `ALWAYS_ON_NOTIFICATION_EVENTS`, `SCHEDULED_NOTIFICATION_EVENTS`; and `defaults.json` in the template folder | `app/Models/Externals/DirectPaymentNotification.php:43–70`; `resources/js/portal/admin/html/views/directpayments-form.html` ~359–372; `resources/js/portal/admin/controllers/direct_payments/directpayments.ts:436–437, ~607`; `…/mjml/defaults/dp/defaults.json` | Adding an event is up to six edits and one is easy to forget | Medium |
| **M8** | **The public SDK exposes the configuration.** `GET /directpayments/{dpRef}/notifications` (unauthenticated) returns `event`, `days_before`, `active` for `dp.notifications.list()/get()` | `DirectPaymentNotificationController::publicList()`; `resources/js/external/api/direct_payments/api.ts`; `portal.d.ts` | The extraction must keep this contract (or version it deliberately) | Medium |
| **M9** | **The scheduler guard and the scheduled query are Direct Payments specific.** `direct_payments:subscription-notify` runs every 15 minutes on the Brain and every tenant clone, guarded by `DirectPaymentNotification::where('is_active', true)->exists()` | `routes/console.php:45–49`; `DirectPaymentsSubscriptionNotify.php` phase 0 | A generic scheduler must keep "zero work when nothing is configured" without a Direct Payments table | Medium |
| **M10** | **The webhook handler sends the e-mail itself, inside the provider's request.** `dispatchEvent()` runs `dispatchToRecipients()` → `DirectPaymentMailer::send()` → `MailHandlerSender::send()` synchronously from `ProcessorWebhookController`. The receipt path, by contrast, is queued with a delay | `ProcessorWebhookController.php:634–639` calling `NotificationDispatcher::dispatchEvent()` (130–159) → `dispatchToRecipients()` (168–217) | A slow mail provider delays the webhook response; the payment provider may then retry the webhook | Medium |

## 1.3 Analytics — `A1`–`A9`

Analytics is `laravel_analytics_events` (module, event, resource_name, resource_reference, route, metadata JSON), `laravel_analytics_daily_rollups`, the models
`AnalyticsEvent` and `AnalyticsDailyRollup`, `AnalyticsApiController`, the browser helper `resources/js/external/api/analytics/api.ts`, the dashboard screen
(`AnalyticsController.ts`, `views/analytics.ts`) and `WwwAnalyticsProvider` for afs-connect.

| ID | Finding | Evidence | Consequence | Severity |
|---|---|---|---|---|
| **A1** | **The server records no analytics event of its own, and the one writer is public and unvalidated.** `POST /portal/api/v1/analytics/events` is listed as a public route and throttled at 600 per minute; it accepts any `module` and `event` string up to 64 characters and any `metadata` array. No `grep` hit in `app/` writes an `AnalyticsEvent` except this controller | `AnalyticsApiController::create()` lines 20–41; `RoutePolicy.php:52`; `routes/portal.php:902` | Payments, sign-ups and bookings never appear; anyone can write fake traffic | High |
| **A2** | **The rollup table is never written.** `AnalyticsDailyRollup` and `laravel_analytics_daily_rollups` have readers (`WwwAnalyticsProvider`) and no writer | `grep -rn "AnalyticsDailyRollup\|laravel_analytics_daily_rollups" app routes database` — only the model, the migration and the provider | A dead table that looks like a feature | Medium |
| **A3** | **The afs-connect analytics summary always reports 0 page loads.** `summary()` uses the rollup table whenever it exists (it always does after migration) and sums `module = 'page'`, `event = 'load'` — values nothing writes (the browser sends `system`/`page_load`, `forms`/`page_load`, `subscribers`/`page_load`) | `WwwAnalyticsProvider.php:27–36`; `analytics/api.ts` `initPageLoad`, `forms.*`, `subscribers.*` | The connect index shows "0 page loads (30d)" on a busy site **(inferred from the code; not observed)** | Medium |
| **A4** | **`summary()` is O(events) in memory and O(days × events) in CPU.** It loads every event in the window with `->get()` (up to 365 days) and then, for each day, filters the whole collection | `AnalyticsApiController::summary()` line 82 and the loop at 169–182 | Slows with traffic and eventually exhausts memory | High (scales badly) |
| **A5** | **Several dashboard numbers are not what their labels say.** `totalVisitors` equals `pageViews` (both are `page_load` counts); `bounceRate` is derived from form loads and completions, not sessions; per-page `bounceRate` is a constant 0; `avgDuration` depends on a `duration` the client may or may not send | `summary()` lines 96–101, 160–162, 191 | Misleading figures on a screen owners act on | Medium |
| **A6** | **The vocabulary is inconsistent.** The same idea is `system`/`page_load`, `forms`/`form_loaded`, `subscribers`/`page_load` in the events table and `page`/`load` in the rollup reader; nothing defines the allowed values | `analytics/api.ts`; `WwwAnalyticsProvider.php` | Reports cannot be combined | Medium |
| **A7** | **Business reporting is separate from the event log, with no link between them.** `EventReportingService`, `AppointmentReportingService` and the money ledger read their own tables ("reports read the rows" — events step 13 §13.2); nothing ties a payment to a funnel or a timeline | `EventReportingService.php`, `AppointmentReportingService.php`, `MoneyController` | No cross-module "what happened on my site this week" | Medium |
| **A8** | **Dead legacy code.** `analytics_update()`, `save_analytics()`, `get_analytics()` call `Input::get` and an `analytics` table from the pre-Laravel stack; nothing references them | `FunctionsController.php:1174–1215`; no caller in `routes/` or `app/` | Confusing, and a trap for the next reader | Low |
| **A9** | **Development seeders fill the tables with invented data.** When the tables are empty and `APP_ENV` is not `production`, `DatabaseSeeder` inserts fake notifications and 610 fake analytics events | `database/seeders/DatabaseSeeder.php:66–72`; `AnalyticsEventSeeder.php` | The dev server's Analytics screen shows traffic that never happened | Low |

## 1.4 Cross-cutting — `X1`–`X3`

| ID | Finding | Evidence | Consequence | Severity |
|---|---|---|---|---|
| **X1** | **"Notification" names three different things:** `App\Models\Notification` (the bell), `DirectPaymentNotification` (an e-mail setting), and an e-mail send. It also collides with Laravel's own `Illuminate\Notifications\Notification` vocabulary | `app/Models/Notification.php`; `app/Models/Externals/DirectPaymentNotification.php`; `NotificationDispatcher` | The class name promises system notifications and delivers e-mail | Medium |
| **X2** | **A module-agnostic payment hook already exists and only queues a mail.** `ChargeSucceeded::handle()` runs once per successful charge for every provider and charge type, under a lock, recording `metadata.mail_queued_at` on the invoice | `app/Externals/DirectPayments/ChargeSucceeded.php:24–52` | It is the natural place for "a payment was made" to be published — one call site, already idempotent | — (opportunity) |
| **X3** | **Direct Payments already publishes domain events** (`SubscriptionEnded`, `SubscriptionMigrated`, `SubscriptionPlanChanged`, …) but nothing consumes them for notification or analytics | `app/Externals/DirectPayments/Events/` (7 classes); `AppServiceProvider.php:103, 106` registers two listeners | Precedent exists for "say what happened"; the plan reuses the idea | — (opportunity) |

## 1.5 Data growth — `D1`–`D8`

Facts for [08](08-data-lifecycle.md). Evidence is in that file's §8.1; the findings are listed here so they are numbered with the rest.

| ID | Finding | Evidence | Consequence | Severity |
|---|---|---|---|---|
| **D1** | **Nothing prunes a tenant site.** The scheduler has six commands and none deletes old rows; no `queue:prune-failed`, `queue:prune-batches` or `model:prune` is scheduled and no model is `Prunable`. The only prune command (`brain:storage-prune`) is Brain-only | `routes/console.php:19–77`; `BrainStoragePrune.php` | Every log table below grows for the life of the site | High |
| **D2** | **`laravel_analytics_events` is unbounded and unindexed by time.** One row per page load and tracked action, with single-column indexes on `module`, `event`, `resource_name`, `resource_reference` only; the summary range-scans `created_at` with no index | `2026_04_04_000001_create_laravel_site_content_tables.php:135–146`; `AnalyticsApiController::summary()` line 82 | The largest table on a busy site; slow reads and no cheap way to trim it | High |
| **D3** | **`laravel_processor_webhooks` keeps the full JSON payload of every webhook forever**, and is also read back (`squareSubscriptionForOrder()`, the Stripe v2 replay guard), so it cannot simply be emptied | `ProcessorWebhookController.php:203, 1217–1229, 1692`; table has `payload` JSON and no time index | Large rows accumulate; a careless prune would break a payment lookup | Medium |
| **D4** | **The send ledger is never trimmed, and a `pending` row left by a dead job holds the unique key forever** | `insertPendingLedgerRow()`; ledger unique key | Growth, and a permanently blocked notification with no visible reason | Medium |
| **D5** | **Small logs grow quietly.** Webhook rejections (one row per rejected call, indexed by IP — an attacker can fill it), webhook orphans, `websocket_failure_events`, `laravel_integration_logs` (JSON payload), `progress_records`, `laravel_form_events` | `2026_05_21_000001_create_processor_tables.php`; chat schema; platform tables; forms tables | Slow, steady growth nobody is watching | Medium |
| **D6** | **Expired credentials are never deleted:** site-user sessions (`expires_at`, `revoked_at`), verification tokens (`expires_at`, `consumed_at`), portal tokens (`laravel_user_tokens.expires_at`) | `2026_08_31_180000_create_site_users_schema.php:85–115`; `0001_01_01_000000_create_users_table.php` | Table growth and a larger pool of stale secrets than needed | Medium |
| **D7** | **Most of those tables cannot be pruned cheaply:** no index on the time column for `laravel_analytics_events`, `laravel_processor_webhooks`, `laravel_integration_logs`, `websocket_failure_events`, `progress_records` (`date`), `laravel_user_tokens` (`expires_at`); the rejection and orphan tables are indexed by `ip` / `provider` first, which a time-only delete cannot use | the create migrations | A delete by age scans the whole table and holds locks for as long | Medium |
| **D8** | **No size monitoring and no way to reclaim disk.** InnoDB `DELETE` does not shrink the file; nothing reports table sizes, and nothing fails when a new log-style table is added without a retention rule | none exists | The problem is invisible until a disk fills | Medium |

## 1.6 What the audit did not find

- A global kill switch for e-mails (no master toggle in the form or the dispatcher) — the only switches are per Direct Payment per event.
- A second writer of `laravel_analytics_events`.
- A second consumer of `NotificationDispatcher` outside Direct Payments.
- Any per-admin or per-site-owner delivery of an inbox notification.
