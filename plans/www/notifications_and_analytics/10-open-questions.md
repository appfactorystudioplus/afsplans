as soon as the plan is approved. **OQ3, OQ7 and OQ13 change what existing sites do**, so they should be decided before P2. **OQ18 and OQ21 decide what the cleanup job may delete and when it is switched on**, so they must be answered before P7.

Reopen any of them if that was not intended. |
| 2026-10-19 | **The money rule** (not a numbered question) | **Owner: a module that uses Direct Payments knows nothing about money — Direct Payments confirms the payment, the Money section records it, Direct Payments controls it — and Direct Payments knows nothing about any other module.** The façade model of the Ecommerce decoupling audit is the pattern. Consequences in [11](11-module-adoption.md) §11.1.2, §11.1.2b and §11.13: module announcements never carry money; Events, Appointments and Sponsorships are refactored like Ecommerce (phases F2–F4); Direct Payments loses its one module name (F5, gate G11); the payer-receipt suppression is a generic invoice option, not module knowledge. |
| 2026-10-19 | **OQ33** — Sponsorships and money; and the exact meaning of the money rule | **Sponsorships works exactly like Ecommerce, down to every detail** (payment through Direct Payments; the module keeps references only, including for its levels, which map to Direct Payments items); **a sponsor sees their own payments and donations in the sponsor dashboard by a one-way read of Direct Payments.** **Reading is allowed: module → Direct Payments → processor** (a module may query any fact it needs, so Ecommerce reading the currency is fine). **The hard stops are: Direct Payments knowing about any other module, and a module managing money data** (Appointments' `paid_cents`). Replaces the earlier "separate follow-up" wording. |
| 2026-10-19 | **OQ7, follow-up** — which events notify by default | **Payment failed and subscription canceled notify by default, bell and e-mail, as the plan proposed.** With the payer's receipt (e-mail) and the four compulsory processor-change e-mails these are the only events on by default; everything else is off until someone switches it on in the Direct Payment's Notifications card. A failure shows on the bell as danger, a cancellation as warning. (`DirectPaymentsActivityModule::NOTIFY_BY_DEFAULT`.) |
| 2026-10-19 | **OQ23** — Brain tables | **Prune the mail log at 90 days.** `brain_app_mail_log` gets a Brain-scope policy (`brain_mail_log`, 90 days), run by `data:prune-brain`, scheduled from `members` and allow-listed in `BrainCommandsController`. `brain_app_mail_events` is **not** a log (it is each app's catalogue of e-mail events) and stays. Everything else Brain-side stays under `keep` until decided table by table. |
| 2026-10-19 | **OQ16** — which module adopts the system first | **Forms**, then Sponsorships, Ecommerce, Events, Appointments, Site Users, Subscribers (as recommended). |
| 2026-10-19 | **OQ2** — read state in the admin inbox | **One flag, global** (as built and as today). |
