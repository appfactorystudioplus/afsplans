## E1 — `bin/set-surface-keys.sh`: one command to give every Brain env file its seven app surface keys (2026-10-10)

Owner request: set `BRAIN_SURFACE_KEY_MEMBERS`, `_NOTES_EDITOR`, `_FLOW_EDITOR`, `_GRAPH_EDITOR`, `_PDF_EDITOR`, `_COORDINATOR` and `_MARKET` in every `.env` in `w/www` except `_env/www/.env`, following what the plans say
([08 §8.2](../08-security-and-safety.md), [`plans/07-www-env-variables.md`](../../07-www-env-variables.md) "`BRAIN_SURFACE_KEY_<APP>`", `billing/08` §8.2): 64 random hex characters, one **distinct** key per app and environment, each equal to that app's
`WWW_BRAIN_SURFACE_KEY`, `_NEXT` (rotation) untouched.

- **Script:** `packages/afsserver/bin/set-surface-keys.sh` (bash; there is no PowerShell twin, unlike `use-env`). Targets: `w/www/.env` and `w/www/_env/{dev,lab2,local,prod,vagrant,vagrant-lan}/.env`. **Never** `_env/www/.env` (the tenant template), and backups are never targets. It refuses a file without `IS_BRAIN=true`.
- **Default behaviour fills gaps only:** an empty or missing key gets a new value from `openssl rand -hex 32`; a value that is already there is kept (it is probably already paired with an app); a value that is not 64 hex characters, or that two apps share, is reported, not changed. The `_NEXT` lines of a key it has to add are added empty. Line endings (LF or CRLF), quoting and every other line are preserved. A timestamped backup `.env.bak-surfacekeys-<stamp>` is saved beside each file it writes. Secrets are printed as four characters only.
- **Options:** `--dry-run`, `--force` (regenerate all seven in the chosen files), `--only <modes>` (`active` is the root `.env`), `--skip-active`, `--root`, and `--sync-apps`, which writes each key into the matching app's `WWW_BRAIN_SURFACE_KEY` for the **same mode** (`w/<app>/_env/<mode>/.env`: members, coordinator, notes, flow, dream_graph, pdf_editor, market) where that is empty (with `--force`, where it differs). It always prints a pairing report (match / app EMPTY / MISMATCH). It never switches a `.env` (`use-env.sh` is a separate command) and does not touch the apps' root `.env` files.
- **State found before writing it:** in `w/www`, the root `.env`, `_env/lab2`, `_env/vagrant` and `_env/vagrant-lan` already hold the same seven keys and every app's matching `WWW_BRAIN_SURFACE_KEY` agrees; `_env/local` has its own set, also paired; **`_env/dev` and `_env/prod` are empty on both sides** ("Not set in this env set: provision a random 64-hex value on both sides before enabling"). So a plain run fills `dev` and `prod` and nothing else, and `--sync-apps` pairs the apps.
- **Verified on a scratch copy of the real files, never on the real ones** (the copy is deleted): dry run writes nothing; a run fills exactly the 14 empty `dev` and `prod` lines (7 each) and nothing else; the lab and `local` files and the tenant template stay byte-identical; with `--sync-apps` all 14 app-side keys equal the Brain side and are 64 hex; a second run changes nothing; a missing key is added after the last surface line and a CRLF file stays CRLF throughout; a duplicate value and a short value are reported (exit 1) and not changed; `--force` replaces all seven; a file without `IS_BRAIN=true` is skipped.
- **Not run on the real files.** The owner runs it. Notes for that: the `_env` sets are tracked by git in `w/www` and in each app (so are the existing `.env.bak-*` files), so the generated `dev`/`prod` values will show up as modified files and the new backups as untracked ones — the same convention that already holds the other production secrets in `_env/prod/.env`, but commit deliberately. The "Not set in this env set" comments above each key in `dev` and `prod` are left as they are and become out of date once the keys are set.

> **Correction to E1 (2026-10-10, later the same day).** E1 said the script preserves CRLF line endings. On this PC (Git Bash, GNU awk 5.0) that was **not true** of the first version: awk strips the CR while reading, so a CRLF file (for example `coordinator/_env/*/.env`) came out as LF and the whole file showed as changed. My check at the time counted CRs with `grep`, which does not count them reliably here. Fixed by running awk with `BINMODE=3`, and re-verified byte for byte (CR and LF counts per file, and a diff with CRs removed to list exactly which keys changed in each file). Nothing was ever run on the real files, so no real file was affected.

## E2 — `bin/set-surface-keys.sh` also sets the four afs-connect service keys (2026-10-10)

Owner request: add `AFS_CONNECT_SERVICE_KEY`, `AFS_CONNECT_SERVICE_KEY_COORDINATOR`, `AFS_CONNECT_SERVICE_KEY_WWW`, `AFS_CONNECT_SERVICE_KEY_MEMBERS` to the script, after checking why they are needed.

**Why they exist** (`plans/afs-connect/06-security-and-service-auth.md`, `plans/07-www-env-variables.md`, `plans/_env/10-coordinator-env-variables.md`, `w/www/config/afs_connect.php`): afs-connect is the app-to-app channel (coordinator, www, members). Every call is signed with HMAC-SHA256 using the **sender's** secret and checked by the receiver with a **copy** of it, so a compromise of one app's key does not compromise the others. In www: `AFS_CONNECT_SERVICE_KEY` is www's own secret and signs www's calls (the coordinator ingest job, the entitlement guard, the settings client); `_WWW` is the same value again (www checks requests that name themselves "www"); `_COORDINATOR` is a copy of the coordinator's own secret and `_MEMBERS` a copy of members' own secret, used by `AfsConnectServiceAuthMiddleware` to verify inbound calls. Pairs: www `SK` = www `_WWW` = coordinator `_WWW`; www `_COORDINATOR` = coordinator `SK`; www `_MEMBERS` = coordinator `_MEMBERS` = members `SK` (members signs its calls to the coordinator in `CoordinatorSettingsClient` and `CoordinatorTokenClient`).

**What the script does with them:** format `afs_` + 43 URL-safe characters (the shape already in the files); fills empty or missing keys; **adopts** a peer's existing secret instead of inventing one (coordinator's `SK` for `_COORDINATOR`, members' `SK` for `_MEMBERS`); keeps `_WWW` equal to `SK`; reports (exit 1) a wrong format, two apps sharing one secret, a `_WWW` that differs from `SK`; `--sync-apps` writes the coordinator's four (`SK`, `_COORDINATOR`, `_WWW`, `_MEMBERS`) and members' `SK` for the same mode; new `--keys surface|connect|all`. The source apps (notes, flow, dream_graph, pdf_editor) and market hold no afs-connect keys in their env sets and are not touched.

**What the state of the real files showed** (read only):
- In `www` and `coordinator` all six modes and the root `.env` have the four/nine keys and **every pair is correct**.
- **All six modes, including `prod`, hold the same secrets** (identical values in dev, lab2, local, prod, vagrant, vagrant-lan). The plan asks for a per-environment secret; these env files are tracked by git, so the production secret is the lab's. The script now reports this ("production values shared with another mode", for the Connect keys and the surface keys). The fix is `set-surface-keys.sh --keys connect --only prod --force --sync-apps` (dry run first); it replaces www's four and the coordinator's and members' prod copies together, so the pairs stay equal. Nothing else holds a copy of those prod values in this workspace.
- **`members` has no `AFS_CONNECT_SERVICE_KEY` in any env set**, although its code signs with it; the coordinator's `_MEMBERS` is set. So members' calls to the coordinator are signed with an empty key. `--sync-apps` writes members' key (the value the coordinator already holds for it).

**Verified on scratch copies of the real files (deleted), never on the real ones:** dry run writes nothing; the default run changes only the empty `dev`/`prod` surface keys; `--keys connect --only prod --force --sync-apps` gives prod its own four secrets and brings the coordinator and members prod files in line (all six pairs equal, three secrets distinct, format correct) while the coordinator's other keys (`_NOTES`, `_FLOW`, `_MARKET`, …), `lab2`, `local` and the tenant template stay byte-identical; a second run changes nothing; a www file with no afs-connect lines adopts the peers' secrets and gets the block appended under a heading, CRLF kept; two equal secrets are reported and not changed; `--keys surface` leaves the afs-connect lines alone; every file's line-ending style is unchanged and only the intended keys differ.

**Not run on the real files.** The owner runs it, with `--dry-run` first. Rotating prod's afs-connect secrets needs the deployed production apps to receive the new values at the same time (each app reads its `.env` at deploy), or calls between them fail until they do.
